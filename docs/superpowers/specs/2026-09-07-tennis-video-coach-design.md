# 网球视频动作分析工具 — 设计文档

日期：2026-09-07
状态：已与用户确认设计，待写实现计划

## 1. 目标与定位

做一个**本地运行、个人自用**的网球视频分析工具。用户上传一段自己练球/对打的视频（手机或相机固定机位，侧面/背面/斜角均可），系统自动：

1. 检测并跟踪画面中的球员；
2. 从整段视频中**挑出 2~3 个拍摄效果最好的击球动作**（不追求逐回合精确切分）；
3. 为每个动作生成一张"准备 / 击球 / 随挥"三帧拼贴图；
4. 通过浏览器自动化，把拼贴图上传到**通义千问网页版**（模拟人工操作，不调用收费 API）；
5. 由大模型判定动作类型（正手 / 反手 / 发球）并给出技术点评纠错与量化评分；
6. 结果返回前端，按动作卡片展示。

### 关键取舍

- **动作类型由大模型判定，本地不训练动作分类模型。** 调研结论：开源界有成熟的球员/球拍/姿态检测（YOLO 系列），但"正手/反手/发球"分类没有开箱可用的预训练权重（Da-233/tennis-vision-analysis 流程最贴合但不含权重，需自备数百 GB 数据训练）。既然图片本来就要发给多模态大模型，动作标注顺势交给大模型，省去训练。
- **不做大模型 API 集成**，用 Playwright 模拟人工操作通义千问网页以规避费用。已知风险：违反站点服务条款、账号可能被限流/封禁、网页改版会导致选择器失效、只能串行。定位为本地个人工具，不做公开多用户服务。
- **不做球场透视检测（homography）**。多机位（侧/背/斜角）没有稳定透视关系，全程只依赖"人 + 网球拍 + 骨架"，对机位鲁棒。
- **择优而非求全**。视频可能很长、含多回合，但球员动作相对固定。系统只挑 2~3 个最清晰的动作分析，不追求覆盖每一回合。

## 2. 整体架构

本地运行，一个 FastAPI 后端 + 一个 React 前端 + 一个持久化 Playwright 浏览器。处理为异步管线，前端通过 SSE 看进度。

```
[React 前端]
  上传视频 → 显示首帧，点选"要分析的球员"（多人画面时）
  进度页（检测…择优…大模型分析第 n/m 个动作）
  结果页：动作卡片（3帧拼贴图 + 动作类型 + 评分 + 点评纠错）
        │ HTTP / SSE
[FastAPI 后端]
  ├── jobs        任务编排：每个视频一个 job，异步执行、记录进度/状态
  ├── cv_pipeline 抽帧 / 检测跟踪 / 挥拍检测 / 质量打分择优 / 拼贴图
  ├── llm_agent   Playwright + 通义千问：登录态、串行队列、上传、抓回复、解析
  ├── storage     job 文件与 result.json 落盘
  └── routes      上传 / 进度 SSE / 结果 / 登录状态
```

### 数据流

视频 → 抽帧(~15fps) → YOLO 检测+跟踪 → 挥拍事件检测 → 质量打分与去重 → 选 2~3 个最优动作 → 每个动作生成三帧拼贴图 → 逐张送通义千问 → 解析结构化 JSON → 存 result.json → 前端按动作卡片渲染。

## 3. CV 管线（cv_pipeline）

- **抽帧**：用 OpenCV 按约 15fps 抽帧（可配置），保留帧序号与时间戳。
- **检测与跟踪**：YOLO11（Ultralytics）检测 COCO 类别中的 `person` 与 `tennis racket`（均为自带类别，无需训练）；YOLO11-pose 提取 17 点骨架。用 Ultralytics 内置 ByteTrack 跟踪，锁定用户在首帧点选的那个球员 ID。Mac 上使用 CoreML/MPS 加速。
- **挥拍（击球瞬间）检测**：跟踪目标球员的网球拍框；拍太小/模糊/缺失时回退用持拍侧手腕关键点。计算帧间位移速度并做平滑，**速度峰值即击球瞬间**。
- **关键三帧选取**：对每个速度峰值，取峰值前的局部极小速点（引拍准备）、峰值帧（击球）、峰值后若干帧（随挥）；裁出以球员为中心、带边距的裁剪图，横向拼成一张标注"准备 / 击球 / 随挥"的图。
- **质量打分**：对每个候选击球点打分，依据——球员检测置信度高、人物框足够大且未被画面边缘截断、球拍清晰可见、速度峰值尖锐（明显快于基线）、骨架关键点完整。
- **去重与分散**：同一次挥拍的相邻峰值只保留一个；按时间间隔归到不同回合（间隔 > ~6 秒视为不同回合）。
- **择优**：选 2~3 个质量最高且时间上分散在不同回合的动作。回合开头若检测到"拍/手举过头顶"的抛球姿势，标记"疑似发球"并优先保留一个发球名额，其余选最清晰的正反手击球。最终动作数目标 2~3 个（可配置）。
- **产出**：每个入选动作一张拼贴图 + 时间戳与本地"疑似发球"提示，按动作组织。

### 边界与失败

- 视频无法解码 → 明确报错。
- 全程未检测到人 → 提示"未检测到球员，请更换视频"。
- 没有合格挥拍/质量分都过低 → 提示"未找到清晰动作，请换一段更清晰、球员更完整入镜的视频"。

## 4. 大模型自动化服务（llm_agent）

- **持久浏览器会话**：后端启动时用 Playwright 拉起 Chromium，使用 `persistent_context` 把登录态保留到本地用户数据目录。**首次运行由用户手动扫码/登录一次通义千问**，之后复用；登录过期时前端提示"请重新登录"并弹出浏览器窗口供用户操作。
- **串行队列**：所有提问任务进队列，一次只处理一张拼贴图，模拟真人逐条发送，规避并发风控。
- **单张流程**：新开一个对话 → 上传拼贴图 → 填入固定提示词 → 发送 → 轮询等待回复结束（"停止生成"按钮消失 / 回复区文本稳定）→ 抓取回复文本。
- **提示词约束返回 JSON**，要求模型仅返回结构化结果，形如：
  ```json
  {
    "stroke_type": "forehand | backhand | serve",
    "scores": {"准备": 8, "击球点": 7, "随挥": 7},
    "overall": 7.5,
    "issues": ["..."],
    "advice": "..."
  }
  ```
- **宽松解析**：容错 ```json 代码块包裹、前后多余文字；解析失败时把原始文本一并保存，前端仍可展示原文。
- **选择器集中配置**：通义千问页面选择器（上传按钮、输入框、发送按钮、回复容器等）集中在一个配置文件/模块，网页改版时只改这一处。
- **节流与重试**：请求间加随机延时；单张失败自动重试 1~2 次；仍失败则该动作标记"分析失败"，不影响其他动作。

## 5. 后端组件与存储

- **模块划分**：`jobs`（编排/进度）、`cv_pipeline`（见 §3）、`llm_agent`（见 §4）、`storage`（文件与结果）、`routes`（HTTP/SSE 接口）。各模块通过明确函数接口调用，可独立测试。
- **存储布局**（无数据库，结果落盘 JSON，重启可恢复）：
  ```
  jobs/<job_id>/
    video.<ext>        原视频
    frames/            抽帧/裁剪中间产物（可定期清理）
    montages/          每个动作的三帧拼贴图
    result.json        结构化结果
  ```
- **进度推送**：SSE 推送阶段进度——上传 → 检测中 → 择优 → 大模型分析 n/m → 完成/失败。
- **主要接口**：上传视频并建 job；查询登录状态 / 触发登录窗口；SSE 订阅 job 进度；获取 job 结果（含拼贴图静态资源）。

## 6. 前端（React）

- 上传区（拖拽/选择视频）。
- 首帧球员点选：多人画面时在首帧上框选/点选要分析的球员。
- 进度页：分阶段进度 + "大模型分析 n/m"。
- 结果页：动作卡片列表，每张卡片含三帧拼贴图、动作类型（正手/反手/发球）、各项评分与总分、问题与建议；解析失败的动作展示原始回复文本；分析失败的动作显示失败状态。

## 7. 测试策略

- **CV 纯函数单测**：速度峰值检测、质量打分、三帧选取与拼贴裁切，用短样本视频/合成数据测试。
- **LLM 解析器单测**：用多组真实/伪造回复（含代码块包裹、多余文字、非法 JSON）测试 JSON 抽取与回退。
- **Playwright 站点交互**：依赖登录态，不进自动化 CI，提供可单独手动验证的入口。
- **端到端**：用一段本地短视频手动跑通 上传→选球员→择优→出图→大模型→结果 的完整黄金路径。

## 8. 技术栈

- 后端：Python 3.10+、FastAPI、Uvicorn；Ultralytics(YOLO11 / YOLO11-pose)、OpenCV、NumPy；Playwright。
- 前端：React + Vite + TypeScript。
- 运行：本地 macOS（CoreML/MPS 加速）；浏览器自动化用本机 Chromium。

## 9. 明确不做（YAGNI）

- 不做球场透视/俯视坐标、球速/跑动距离统计。
- 不训练本地动作分类模型；动作类型由大模型判定。
- 不逐回合精确切分、不覆盖所有回合，只择优 2~3 个动作。
- 不做多用户/账号体系/公网部署/任务并发。
- 不集成收费大模型 API（本期）。
- 不做比分/比赛记分。
